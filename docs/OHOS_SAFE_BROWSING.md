# 恶意网站与钓鱼检测（Safe Browsing）实施规范

状态：2026-10-07 规范，尚未实施。实施分两阶段：**第 0 阶段只做调研和方案，交给用户决定后才进入第 1 阶段写代码。**

## 现状

- `config` 与 runner 实际构建均为 `safe_browsing_mode = 0`，Chromium 的 Safe Browsing 组件整体未编译。
- 设置里已有 `safeBrowsing` 偏好（`'off' | 'standard' | 'enhanced'`，`shell_prefs_ohos.cc`），只保存值，不产生任何保护。`SHELL_CONTRACT.md` 已要求设置页不承诺有安全浏览保护。
- 引擎没有任何网址信誉查询。

## 不允许的做法

- 只把 `safe_browsing_mode` 改成 1 或 2。1 需要 Google API 密钥和可访问的 Google 服务端，2 依赖 Android 的 Google Play 服务（鸿蒙上不存在），都不能直接工作，还会引入大量无效后台请求。
- 在用户不知情时把完整网址发给第三方。
- 以“编译通过”“接口返回成功”代替真机拦截验收。

## 第 0 阶段：调研与方案（先交付，不写代码）

逐项核实以下候选服务，结论写进本文“调研结论”一节，标明每一条是**已核实**（附官方文档链接或真机结果）还是**推测**：

| 候选 | 需要核实 |
| --- | --- |
| Google Safe Browsing（Update API v4/v5，Chromium 原生支持） | 官方条款写明 Safe Browsing API 仅限非商业用途，商业用途要用付费的 Web Risk API；Lumie 属于哪一类。Web Risk 能否接入 Chromium 现有的本地数据库更新逻辑，改动多大。中国大陆网络能否访问其服务端；不能访问时的表现（数据库永远为空、只是没保护，还是拖慢导航）。API 密钥的申请、配额、密钥放在哪里（不得写进公开仓库）。 |
| 华为 Device Security Kit / Safety Detect 的 URL 检测（URLCheck） | 公开资料显示 HMS Core 版 URLCheck 支持 EMUI 4.0–HarmonyOS 4.0 和 Android 设备；**HarmonyOS NEXT（API 12+）上是否有对应接口、接口名、最低 API 版本**。接入条件：AppGallery Connect 注册、签名、`client_id`、是否收费、配额与调用频率限制。返回的威胁类型（钓鱼、恶意软件、不良内容等）。是否要求传完整网址，能否只传协议 + 主机 + 路径。网址发送到华为服务器的隐私说明，以及是否需要在隐私政策中声明。单次查询的真机延迟（测 20 次，记中位数和最大值）。 |
| 国内商业网址安全接口（如腾讯、360 等） | 只做概况：是否面向浏览器开放、计费方式、合同要求。不深入。 |

每个候选还要回答：

1. 目标用户所在地（以中国大陆为主）能否用。
2. 隐私：发出去的是什么（完整网址、去掉查询参数的网址、哈希前缀），发给谁，用户能否关闭。
3. 失效时的行为：服务超时或不可用时，必须**放行**（fail-open），不能让用户打不开网页。
4. 成本与条款风险。

## 第 1 阶段：实施约束（以华为 URLCheck 为例，选别的方案时按同样原则调整）

### 检查范围

- 只检查 http / https 的**顶层（主框架）导航**，包括重定向后的最终网址。子框架、子资源、下载不在第一期范围内，文档写明。
- 跳过：内网与本机地址（`localhost`、私有网段、`.local`）、`chrome://` 等内部页面、`file:`、`data:`、`blob:`。
- 无痕窗口同样检查（与 Chrome 一致），但不缓存到磁盘。
- `safeBrowsing` 为 `off` 时完全不查询；`standard` 时启用；`enhanced` 第一期与 `standard` 相同，文档注明，不承诺更多。

### 内核结构

- 用 `content::NavigationThrottle` 实现，在 `WillProcessResponse` 等结果，让查询和网络请求并行，不在 `WillStartRequest` 阻塞。重定向时查询新网址。
- 查询放到外壳实现的系统服务（`registerShellSystemService('urlcheck', …)`），内核通过现有系统服务桥调用。HMS / Device Security Kit 的接口可能超出引擎 HAR 的 API 20，与 `passwordvault` 相同处理。服务协议写进 `SHELL_CONTRACT.md`：请求 `{ url }`，回复 `{ verdict: 'safe' | 'phishing' | 'malware' | 'unwanted' | 'unknown' }`。
- 超时（建议 1.5 秒，按真机延迟定）或出错一律按 `unknown` 放行，并计数。
- 结果在内存里按主机名缓存，安全结果保留时间短（如 5 分钟），危险结果保留长一些（如 30 分钟）；进程退出即丢失。不写磁盘。

### 拦截页

- 命中危险结果时显示拦截页，复用 Chromium `components/security_interstitials` 的通用页面框架，不要自己画一套。
- 文案：说明风险类型，主按钮“返回安全页面”（有历史就后退，没有就打开新标签页），次要入口“详细信息 → 仍要访问”。
- 用户选择“仍要访问”后，本次会话内对该主机放行。
- 中文文案由内核提供，外壳不需要改。

### 设置与外壳

- 设置页文案在功能真机验收前保持不承诺保护；验收通过后更新 `SHELL_CONTRACT.md` 的 `safeBrowsing` 说明，并通知外壳调整设置页文案和隐私说明。
- 外壳侧需求单独写到 `docs/engine-requests` 风格的说明里交给外壳：实现 `urlcheck` 服务、AppGallery Connect 配置、隐私政策条目。

### 日志与隐私

- 日志只记计数和结果类别，网址一律用 `UrlForLog()`（只留协议和主机），不记查询参数，不记完整的服务返回内容。
- 不新增网址的磁盘持久化。

## 工程规范（与其他项相同）

- 修改上游文件必须新增增量补丁：先只读取得 runner 当前文件（`/root/chromium-154/src`，只读），改完用 `git diff --no-index` 生成，在本地隔离目录模拟 `apply_incremental_patch` 的首次应用、重复应用和旧版升级，登记到 `scripts/ci-incremental-build.sh`。**不能手写补丁。**同一文件上的多个补丁修改段不能相邻。
- 新源文件放 overlay；新增 GN 依赖要放在已初始化的 `deps +=` 列表里。
- 只在 CI 编译，不在本地编译。
- 同一时间只有一个 agent 往 `hmos-154-adapter` 推送；推送前先拉取。
- 不操作真机，真机验收由协调者执行。

## 验收（由协调者在真机上执行）

1. 服务方提供的官方测试网址（钓鱼、恶意软件各一个）被拦截，显示正确的风险类型；需在第 0 阶段找到这些测试网址。
2. 普通网站不被拦截；打开 20 个常用国内网站，记录首屏时间，开启与关闭检测对比，差异需在可接受范围内（第 0 阶段给出标准）。
3. 断网或服务超时时网页照常打开（放行）。
4. “返回安全页面”和“仍要访问”行为正确；放行只在本次会话内有效。
5. `safeBrowsing` 设为 `off` 后不再发出任何查询（hilog 计数为 0）。
6. 无痕窗口同样拦截，且不留下缓存文件。
7. hilog 里搜不到被检查网址的路径和查询参数。
8. 手机单进程与平板 / PC 多进程各测一遍。
